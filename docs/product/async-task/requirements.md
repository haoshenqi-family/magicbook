# async-task 核心异步任务体系 · 需求基线

> 状态：**目标态，R240 设计已落，尚未实现**（2026-10-28）。
> 定位：magicbook 的内部核心工程模块，不是用户直接操作的产品模块。
> 接口与 SPI：[`interface.md`](./interface.md)；运行时边界：[`features/runtime.md`](./features/runtime.md)；
> 新任务设计准入：[`features/task-authoring.md`](./features/task-authoring.md)。

## 1. 模块范围

本模块负责 magicbook 中所有**跨请求、可恢复、用户可感知或会产生外部副作用**的异步工作：

- 整本翻译的发布、外部执行对账与完成回收；
- 整本朗读的逐段合成与重试；
- 全文单词详解预览、按书补缺；
- 未来的导入、导出、批处理、定时维护等长任务；
- 其他需要进度、取消、重试、重启恢复或费用审计的业务任务。

以下场景不属于本模块：

- 单次 HTTP 请求内的元数据并发查询、数据库读取等短生命周期 fan-out；
- 只影响当前请求、丢失后可由用户重试且无持久副作用的纯内存并发；
- Web 服务器自身的进程守护、镜像健康检查和容器编排。

“短生命周期 fan-out”必须受请求生命周期和固定并发上限约束，不能演变成事实上的后台任务。

## 2. 核心需求

### R240-1 数据库是任务状态的唯一事实源

- job、item、重试时间、执行租约、外部任务引用和最终结果必须持久化到数据库。
- 进程内线程、队列、锁和集合只能用于唤醒、调度和性能优化，不能作为任务是否存在的权威判据。
- 进程重启后，系统必须只依赖数据库恢复任务，不依赖旧进程遗留的内存状态。

### R240-2 单进程部署也必须具备可恢复性

- magicbook 当前继续以单个 Web 进程部署，本轮不拆分 `web` 与 `worker`。
- 部署重启允许短暂停止后台执行，但不得让已受理任务永久停在 `RUNNING`。
- 每个 item 必须有可提交的断点；重启后最多重做当前 item，不能整批从零开始。

### R240-3 有界执行与背压

- 后台执行必须经过统一的有界 worker 池，不允许每个 job 任意创建常驻线程。
- 必须同时限制全局并发、任务类型并发、单 job 并发和上游供应商并发。
- 队列积压不能导致内存无界增长；待执行事实保存在数据库中。

### R240-4 租约、心跳与 fencing

- worker 通过数据库 CAS 领取 item，并获得唯一租约令牌。
- 长任务执行期间必须持续续租；进程崩溃或失联后，过期租约可被安全回收。
- item 的最终写回必须携带 owner 与租约令牌作为 fencing 条件；失去租约的旧 worker 不得覆盖新 worker 的状态。
- `updated_at` 只能用于展示或辅助排序，不能单独承担“是否仍存活”的判据。

### R240-5 至少一次执行 + 业务幂等

- 运行时承诺：任何可执行 item 最终至少被尝试一次；进程在“外部副作用已发生、本地结果尚未提交”之间崩溃时，允许再次尝试。
- 每个会产生外部副作用的处理必须定义稳定幂等键，并通过上游幂等、内容寻址缓存、先查后建或等价机制避免重复计费、重复写入和重复发布。
- 上游若无法提供任何幂等或可查询凭据，该任务不得声明“不会重复执行”，必须在 LLD 中显式登记风险。

### R240-6 item 级断点与可重试失败

- producer 必须把批任务拆成稳定、可单独重试的 item。
- item 完成后立即提交结果和进度；不得等整批结束才统一落库。
- 可重试错误进入退避队列，永久错误进入失败终态；必须有最大尝试次数，禁止无限重试。
- 单个毒 item 不得阻塞整个 job；job 最终可进入 `PARTIAL_FAILED` 并让用户看见失败范围。

### R240-7 取消与重试语义明确

- 取消必须写入数据库，并阻止后续领取。
- 已提交给外部系统的任务，若上游不支持取消，必须明确表现为“本地停止继续投递，远端已受理部分仍可能完成”。
- 手工重试只能重新排队指定失败 item，不得复活已取消 job。

### R240-8 优雅停机与部署窗口

- 应用收到 `SIGTERM` 后必须立即停止领取新 item，并在配置的 drain 窗口内完成当前安全点或释放租约。
- 容器 grace period 必须大于应用 drain 窗口。
- 部署不得依赖“线程可能在进程退出前刚好跑完”；恢复能力必须由数据库租约与启动恢复保证。

### R240-9 可观测与失败可见

- job / item / attempt 必须可追踪，日志至少包含 `job_id`、`item_id`、`attempt`、`instance_id`、`external_ref` 和稳定错误码。
- 用户可感知任务失败时，前端必须显示真实失败状态或明确的重试状态，不能伪装成“仍在加载”或“没有数据”。
- 核心运行时必须提供队列积压、最老待执行、运行中、租约回收、失败率和吞吐等可观测信号。

### R240-10 安全和身份

- 不把用户 JWT、refresh token、API Key 或其他可直接复用的凭据写入 job/item payload。
- 后台执行使用服务身份或受控凭据引用；job 中只保存不可变的发起用户 id、计费归属和必要授权上下文引用。
- 日志和状态接口必须脱敏，不输出 prompt 全文、书籍正文或凭据。

### R240-11 单进程不是绕过核心模块的理由

- 任何新增异步任务都必须接入本核心模块；不得再新增自管 daemon 线程、进程内任务队列或以 `updated_at` 判活的私有实现。
- 现有整本翻译、整本朗读、全文单词详解预览/批次属于迁移债务，不能作为未来实现模板。
- 例外必须先获得用户明确批准，并形成 ADR 说明为何不能使用核心模块、如何恢复、如何防重和何时归还。

### R240-12 保留未来拆分能力，但本轮不拆

- 核心运行时与业务 handler 必须解耦，数据协议不得依赖 Flask request/session。
- 未来若发布隔离成为真实瓶颈，可只把同一套 handler 与 runtime 迁到独立 `magicbook-worker`。
- 拆分不改变任务语义；多进程运行前必须评估 SQLite 写锁，并迁移到支持可靠行级锁的数据库。

## 3. 非目标

- 本轮不引入 Celery、RQ、Kafka、RabbitMQ、Redis 作为任务事实源。
- 本轮不实现 Web/Worker 微服务拆分。
- 本轮不修改 moon-well 的任务执行或缓存实现。
- 本轮不写运行时代码、不建表、不改部署配置。
- 本轮不自动迁移现有活动任务；迁移脚本与切换顺序在实施阶段按 LLD 执行。

## 4. 成功判据

1. 任意时刻重启 magicbook，已受理任务在租约过期后自动继续，不永久卡在 `RUNNING`。
2. 同一 item 不会因为两个线程或两个进程同时执行而产生无保护的双重外部副作用。
3. 长任务停机窗口有上界，部署后用户能看到进度继续推进或明确失败。
4. 新 Agent 在设计和评审异步任务时，能从 `AGENTS.md` 直接找到唯一规范并逐项自检。
