# 新异步任务设计与实现准入清单

> 状态：**强制规范，2026-10-28 R240 起生效**。
> 适用：任何新增或改造 magicbook 异步任务的人 / Agent。
> 权威架构：[`runtime.md`](./runtime.md)；需求基线：[`../requirements.md`](../requirements.md)。

## 1. 先判断是否真的需要后台任务

按顺序判断：

1. 能否在请求超时内可靠完成？能则同步执行。
2. 是否只是同一请求内的并行 I/O？是则使用有界 `ThreadPoolExecutor` 或现有安全 fan-out，不落业务任务。
3. 是否有用户可见进度、外部计费、批处理、重试、取消或重启恢复需求？有则必须使用核心异步任务模块。
4. 是否能在 5 秒内完成且失败后用户可无成本重试、没有任何持久副作用？可保持同步或请求级并发。

只要出现“用户关掉页面后还要继续”“部署后不能丢”“失败要自动重试”“会产生 LLM/TTS 费用”之一，就属于核心模块范围。

## 2. 设计阶段必须回答的十一个门禁问题

LLD 缺少任一项，不得进入编码：

1. **任务身份**：`job_type` 是什么？`job_version` 从几开始？
2. **拆分粒度**：job 与 item 各是什么？`item_key` 为什么稳定？
3. **最大损失**：进程在任意时刻崩溃，最多重做多少工作？
4. **幂等键**：每个外部副作用使用什么键？上游是否真正支持幂等或可查询？
5. **重试策略**：哪些错误可重试？最大次数、退避、`Retry-After` 如何处理？
6. **断点**：item 内有哪些阶段？`checkpoint_json` 在什么安全点提交？
7. **取消语义**：本地停止、上游停止、不可撤回分别如何呈现？
8. **权限与身份**：执行时用什么服务身份？如何保留 owner 与计费归属？是否误存用户 token？
9. **并发与背压**：全局、类型、job、用户、上游 quota 各是多少？
10. **失败可见**：用户看到什么状态？如何区分等待重试、部分失败和永久失败？
11. **验证方式**：如何注入“领取后崩溃、外部成功后本地提交前崩溃、心跳丢失、部署 SIGTERM”？

## 3. 必须使用的运行时能力

- 通过 producer API 创建 job + item；
- 通过 handler registry 注册 `job_type/job_version`；
- 通过数据库 CAS 租约领取；
- 通过 heartbeat 续租；
- 通过 `ItemContext.save_checkpoint()` 在长 item 的安全点提交中间断点；
- 通过 fenced commit 提交结果；
- 通过统一 recovery 处理过期租约；
- 通过统一 worker pool 和 quota 限流；
- 通过统一 cancel/retry API 控制；
- 通过核心状态 DTO 或业务 DTO 暴露进度；
- 通过结构化日志记录 attempt 与 external ref。

## 4. 禁止事项

以下写法一律不合格：

- 在业务 service 里直接 `threading.Thread(..., daemon=True)` 执行长任务；
- 用进程内 `set` / `dict` / `Queue` 作为任务是否存在的唯一判据；
- 用 `updated_at` 超过 N 分钟代替租约和心跳；
- 每个 job 创建一条永久线程；
- 请求线程里启动后台任务但不先提交 job；
- 任务已提交后才在内存里补 item，崩溃后 job 永远为空；
- 对异常统一 `except Exception: log` 后让 job 永久停在 `RUNNING`；
- 上游未定义幂等就承诺“不会重复扣费”；
- 将用户 JWT、refresh token、API Key 写进任务表；
- 用户已取消后，retry 又把 job 静默复活；
- 把失败伪装成空数组、0 结果或无限加载；
- 新增业务 handler 依赖 Flask `current_user`、request 或 session；
- 以“magicbook 是单进程”为由省略租约、恢复和 fencing。

## 5. Item 设计规则

### 5.1 粒度

优先选择：

- 一次可独立计费的上游调用；
- 一个可独立查询结果的段落；
- 一个大小受控的词批；
- 一个可以幂等重建的解析阶段。

避免：

- 整个 job 只有一个巨大 item；
- 一个 item 内含数万次不可恢复调用；
- 过细到每个字符一行，导致台账和调度开销高于业务本身。

### 5.2 item_key

使用业务稳定键，例如内容 hash、规范化 id 或固定序号。禁止：

- `uuid4()` 作为每次重算的新 key；
- `now()` / 当前批次 id 作为重试后会变化的内容键；
- 把用户可见顺序直接当作唯一身份而不考虑正文变化。

正文变化时，应由新的 job fingerprint 或新 job 表达；同一 job 内 key 不得漂移。

### 5.3 checkpoint

对不可在单个 item 内快速完成的工作，必须定义 checkpoint：

- 解析：已处理章节/段数；
- 缓存扫描：已检查词数/游标；
- 上传：已完成分片；
- 分页抓取：下一页游标。

checkpoint 提交后，恢复从最近安全点继续；checkpoint 不得包含进程内对象、文件句柄或 token。

checkpoint 必须有 handler 自有的 schema version 和大小上限。job 提交使用的 `idempotency_key` 只用于防止重复建 job；item 重试和外部副作用必须使用 `item_key`/操作幂等键，二者不得混用。

## 6. 外部副作用审计

在 LLD 用表列出：

| 副作用 | 幂等键 | 上游支持 | 崩溃后策略 | 失败可见性 |
| --- | --- | --- | --- | --- |
| 例：moon-well `/tts/speak` | 文本 hash + voice/style | 永久缓存自然幂等 | 重试，命中缓存不重复合成/计费 | `message` 显示最终错误 |
| 例：LLM task publish | `jobId:itemId:textHash` | 需实测/确认 | 重试前查已有 taskId | 展示上游 taskId 与失败原因 |

上游支持情况没核实前，写“待确认”，不能写“幂等”。

## 7. 状态与用户体验

每个业务页面至少要能显示：

- 受理成功，job 已排队；
- 当前阶段与可计算进度；
- 当前在等待上游、退避重试还是正在执行；
- 部分失败的数量和原因；
- 是否可取消、取消后已受理部分是否仍会完成；
- 是否可只重试失败项；
- 终态完成后最近更新时间。

轮询频率根据状态源成本设置；页面不可见时暂停。轮询失败不能把已有进度清空。

## 8. 测试要求

每个 task LLD 必须包含以下测试矩阵：

| 场景 | 必须证明 |
| --- | --- |
| 双 worker 同抢 | 只有一个获得租约 |
| 领取后进程被杀 | 租约过期后自动恢复 |
| 外部成功后、本地提交前被杀 | 重试不会造成无保护重复副作用 |
| 旧 worker 迟到写回 | fencing 阻止覆盖 |
| 可重试错误 | 按退避策略重试 |
| 永久错误 | 达终态且用户可见 |
| 毒 item | 不阻塞其他 item |
| 取消 | 不再领取、不复活 |
| SIGTERM / 部署 | 停止 claim，grace 内收敛，超时后可恢复 |
| 状态聚合 | 进度准确，不假完成、不倒退 |

如果某项无法测试，必须在 LLD 说明原因和人工验证证据，不得略过。

## 9. 评审清单

评审者至少检查：

- [ ] 没有绕开核心 runtime 新开业务后台线程；
- [ ] job/item 身份与幂等键稳定；
- [ ] 最大工作损失有明确上界；
- [ ] 所有外部副作用都有崩溃后策略；
- [ ] 错误分类与最大尝试次数明确；
- [ ] 取消/重试语义前后端一致；
- [ ] 没有持久化原始凭据；
- [ ] 有全局、类型、job 和上游 quota；
- [ ] 有统一启动恢复与优雅停机接入点；
- [ ] 有故障注入测试和重启测试；
- [ ] 用户能看到等待、重试、部分失败和最终失败；
- [ ] 文档四问与 LLD 状态行已安排回填。

## 10. 存量任务的特别规则

R240 实施前，现有整本翻译、整本朗读、全文单词详解预览/批次可以继续运行，但：

- 不得把它们复制成新任务的模板；
- 修复现有任务时，优先抽出可迁移到核心 runtime 的语义；
- 若临时仍需修改旧 daemon，必须在 LLD 中登记“迁移债务”；
- 一旦对应适配器迁移完成，旧线程花名册、私有恢复入口和重复状态机必须删除或只读化。
