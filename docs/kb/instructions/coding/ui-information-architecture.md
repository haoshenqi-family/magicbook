# UI 信息架构：MagicBook 长期设计原则

> 为什么建这篇：R251 暴露的问题不是组件不够多，而是入口没有层级——顶栏、Settings、
> 侧栏同时承担导航，页面归属靠零散条件判断，书架名称也无排序与兜底。后续 UI 任务先按本文
> 做设计评审，避免每轮局部修补又堆回同类问题。

## 1. 先分域，再组织页内模块

- 一级域回答“用户现在要完成哪类任务”：首页、书库、学习、账号、管理。
- 页内模块只服务本域任务，不把低频工具提升成一级入口。
- 每个页面最多归属一个域；归属不明确时宁可不点亮，也不用“看起来相关”猜一个。
- 新增域前先证明它有独立任务、不会与现有域重叠，并检查移动端是否仍有位置。

## 2. 一个任务一个主入口

- 同一能力只保留一个主入口，其他入口只能是上下文快捷方式。
- Settings 不是杂物箱；只有“设置/工具”语义明确的能力才放进 Settings。
- 管理员能力属于管理域，不应和书库能力混排。
- 高频读者能力优先，低频管理能力降级；管理入口不能遮挡普通读者路径。

## 3. 展示分组必须安全兜底

- 分类只影响展示时，不改 schema。
- 规则未命中的条目进入“其他/默认”组，绝不隐藏。
- 每个分组提供数量与空组策略；空标题比缺入口更容易修复，但仍应避免空噪声。
- 入口守恒要成为测试：分类前后总数一致，真实模板渲染也算一次。

## 4. 名称含数字时按数值排序

`阶1 < 阶2 < 阶10`，不能依赖字符串字典序。
只要名称参与业务排序，就用显式解析器与降级值，并给非数字尾组稳定顺序。

## 5. 产品层增量，不重写上游

- Calibre-Web 是 vendored 基座：优先新增产品层模块、Jinja filter 和增量 CSS。
- 保留上游组件骨架与关键 DOM ID，避免路由、onboarding 和脚本锚点漂移。
- 不修改 vendored CSS 解决局部问题；用产品层覆盖并写清叠层原因。
- 接入点越少越好：先问“能否在外围判断”，再问“是否必须改上游函数”。

## 6. Active 是状态，不是装饰

- 用单一函数计算当前域，不从多个模板条件重复推导。
- `active` 与 `aria-current` 必须同源。
- 未知页面没有 active 是正确行为；错误点亮比不点亮更伤导航信任。
- 每个新页面都要补“唯一 active”测试。

## 7. 响应式按任务可达性设计

- 桌面用主导航表达五域；手机底栏只放最高频的四类任务。
- 不把桌面的全部入口机械压缩进底栏。
- 悬浮控件必须让出底栏安全区；后加载样式覆盖要有特异度守卫。
- 每次至少验证 1440px 与 390px，检查横向滚动、遮挡和触达面积。

## 8. 视觉层级要克制

- 一级域用位置、间距和下划线表达；页内分组用小标题、竖条与数量徽标表达。
- 不给每个元素都加边框、卡片和阴影，层级越多越需要留白。
- 主题适配优先保持结构不变，只覆盖尺寸、颜色和显隐。
- 空标题、错误 active、被遮挡的底栏都属于结构缺陷，不只是“样式小问题”。

## 9. 评审清单

改动 UI 信息架构前逐项回答：

1. 这项能力属于哪个一级域？是否有唯一主入口？
2. 是否在重复已有入口？
3. 分类规则的兜底是什么？会不会隐藏条目？
4. 是否真的需要改模型或迁移？
5. 关键 DOM ID 是否保留？
6. active 是否只有一个归属？
7. 移动端是否仍可达，是否遮挡底栏？
8. 默认主题与 CaliBlur 是否都检查？
9. 是否有入口守恒和归属测试？

## 10. 触发重新评估的条件

- 用户需要稳定、跨设备、可编辑的书架类型；
- 一级域超过五个或移动底栏需要超过四个高频入口；
- 同一页面出现两个合理的一级域归属；
- 展示分类开始影响权限、同步或排序业务语义。

满足任一条件时，先立独立需求与迁移设计，不在现有展示规则上继续堆特例。
