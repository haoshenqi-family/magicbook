# UI 信息架构：MagicBook 长期设计原则

> 为什么建这篇：R251 暴露的问题不是组件不够多，而是入口没有层级——顶栏、Settings、
> 侧栏同时承担导航，页面归属靠零散条件判断，书架名称也无排序与兜底。后续 UI 任务先按本文
> 做设计评审，避免每轮局部修补又堆回同类问题。

## 1. 先分域，再组织页内模块

- 一级域回答“用户现在要完成哪类任务”：首页、书库、学习、账号、管理。
- 页内模块只服务本域任务，不把低频工具提升成一级入口。
- 每个页面最多归属一个域；归属不明确时宁可不点亮，也不用“看起来相关”猜一个。
- 新增域前先证明它有独立任务、不会与现有域重叠，并检查移动端是否仍有位置。

## 2. 一个任务一个主入口

- 同一能力只保留一个主入口，其他入口只能是上下文快捷方式。
- Settings 不是杂物箱；只有“设置/工具”语义明确的能力才放进 Settings。
- 管理员能力属于管理域，不应和书库能力混排。
- 高频读者能力优先，低频管理能力降级；管理入口不能遮挡普通读者路径。
- 先列“功能树”，再决定路由与页面；不能从一个拥挤页面直接开始摆卡片。
- 一个 L2 页面只承载一个完整用户任务。A 账号的偏好、伙伴、邮件、积分、成就和导出
  必须各自成页；M 管理的用户、内容、资产、运营和系统配置也必须各自成页。
- L2 导航用分组纯文字链接，不用功能卡片。卡片表示“现在可执行的动作”，不表示“页面目录”。
- “伙伴”是 AI 伴读的入口和外观，不是第二套聊天产品；入口页只负责选择伙伴/快捷动作，
  对话、记忆、工具和语音继续复用同一个 AI 抽屉。
- **功能地图要有唯一归属**：用户视角的完整功能树放 L1
  `docs/product/readme/feature-map.md`，产品 README 只提供入口；L3 只引用并描述实现边界，
  不复制第二棵树。两处同时维护必然会漂移。
- **侧栏从属于当前域，不做全局常驻容器**：只有当前域确实需要持续上下文操作时才显示侧栏。
  书库保留 Calibre 原书目侧栏；首页、学习、账号、管理等任务页直接收起侧栏并释放宽度。
  如果新域暂时没有合理侧栏，优先隐藏，不要塞入无关入口或空壳导航。

## 3. 展示分组必须安全兜底

- 分类只影响展示时，不改 schema。
- 规则未命中的条目进入“其他/默认”组，绝不隐藏。
- 每个分组提供数量与空组策略；空标题比缺入口更容易修复，但仍应避免空噪声。
- 入口守恒要成为测试：分类前后总数一致，真实模板渲染也算一次。

## 4. 名称含数字时按数值排序

`阶1 < 阶2 < 阶10`，不能依赖字符串字典序。
只要名称参与业务排序，就用显式解析器与降级值，并给非数字尾组稳定顺序。

## 5. 产品层增量，不重写上游

- Calibre-Web 是 vendored 基座：优先新增产品层模块、Jinja filter 和增量 CSS。
- 保留上游组件骨架与关键 DOM ID，避免路由、onboarding 和脚本锚点漂移。
- 不修改 vendored CSS 解决局部问题；用产品层覆盖并写清叠层原因。
- 接入点越少越好：先问“能否在外围判断”，再问“是否必须改上游函数”。

## 6. Active 是状态，不是装饰

- 用单一函数计算当前域，不从多个模板条件重复推导。
- `active` 与 `aria-current` 必须同源。
- 未知页面没有 active 是正确行为；错误点亮比不点亮更伤导航信任。
- 每个新页面都要补“唯一 active”测试。

## 7. 响应式按任务可达性设计

- 桌面用主导航表达五域；手机底栏只放最高频的四类任务。
- 不把桌面的全部入口机械压缩进底栏。
- 悬浮控件必须让出底栏安全区；后加载样式覆盖要有特异度守卫。
- 每次至少验证 1440px 与 390px，检查横向滚动、遮挡和触达面积。

## 8. 视觉层级要克制

- 一级域用位置、间距和下划线表达；页内分组用小标题、竖条与数量徽标表达。
- 不给每个元素都加边框、卡片和阴影，层级越多越需要留白。
- 主题适配优先保持结构不变，只覆盖尺寸、颜色和显隐。
- 空标题、错误 active、被遮挡的底栏都属于结构缺陷，不只是“样式小问题”。

## 9. 从 R251 得到的教训

- **入口不是功能**：顶栏、Settings、侧栏同时放入口，会让同一能力出现多个“家”。
  先定唯一主入口，其他位置只能做上下文快捷方式。
- **页面不是收纳箱**：把难度、主题、伙伴、导出和积分堆进 `/me`，短期省一次跳转，
  长期会让每个用户任务互相拖慢、互相遮挡，也无法独立验收。
- **角色差异不是布局理由**：用户积分页和管理员积分治理不是“同一页面按角色显隐”，
  而是两个任务、两个权限面；物理拆页比继续加页签更清楚，也更安全。
- **目录不要卡片化**：L2 的功能目录使用文字链接和分组标题即可；每项都套卡片会让
  真正需要强调的状态失去层级。
- **关系要命名准确**：伙伴是 AI 伴读的入口/外观，不是独立聊天域。关系命名错了，
  后续会自然长出第二套会话、第二套记忆和第二套入口。
- **分类必须守恒**：书架名称规则只是展示层，未知项必须有兜底组；不为了分组新增 schema。
- **截图工具也是测试工具**：Headless Chrome 的 `--window-size=390` 可能仍使用 500px
  布局视口。移动验收要用设备指标模拟，并同时断言 `scrollWidth == innerWidth`，
  不能只看裁切后的 PNG。
- **兼容不是继续使用旧壳**：旧 `/admin/view` 可以保留 302 兼容，但新顶栏必须直达新首页，
  否则用户每次都要经过一个已经废弃的仪表盘。
- **侧栏不能跨域借壳**：Calibre 书目侧栏只服务找书与筛选。把它继续挂在账号、学习或管理页，
  用户会误以为这些操作属于书目上下文；正确做法是按一级域显式隐藏，而不是保留空栏。

## 10. 评审清单

改动 UI 信息架构前逐项回答：

1. 这项能力属于哪个一级域？是否有唯一主入口？
2. 是否在重复已有入口？
3. 是否先列了完整功能树，并把每个叶子分到一个页面？
4. 这个页面是否只承担一个用户任务，还是又变成了混合仪表盘？
5. 分类规则的兜底是什么？会不会隐藏条目？
6. 是否真的需要改模型或迁移？
7. 关键 DOM ID 是否保留？
8. active 是否只有一个归属？
9. 移动端是否仍可达，是否遮挡底栏？
10. 默认主题与 CaliBlur 是否都检查？
11. 是否有入口守恒、唯一 active、角色隔离和 390px 真实设备视口测试？
12. 侧栏是否只在真正需要上下文操作的域出现？隐藏后内容是否释放宽度？

## 11. 触发重新评估的条件

- 用户需要稳定、跨设备、可编辑的书架类型；
- 一级域超过五个或移动底栏需要超过四个高频入口；
- 同一页面出现两个合理的一级域归属；
- 一个 L2 页面开始出现两个互不依赖的高频任务；
- 展示分类开始影响权限、同步或排序业务语义。

满足任一条件时，先立独立需求与迁移设计，不在现有展示规则上继续堆特例。
