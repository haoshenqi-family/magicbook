# R272 LLD · 小程序账号体系（自动建号 + 账号页）

## 1. 为什么要改

R271 的登录流程是 R239 两步式的忠实实现：未绑定微信 → 只发票据 → 要求输网页端账号密码。
对老用户正确，对**第一次用小程序**的人是死路——他没有账号可输。

R240 在后端把默认路径改成「未绑定即建临时账号」，本次小程序跟上，并补一个能完成
「绑定邮箱 → 认领老账号」的界面。

## 2. 页面与状态

### 登录页 `pages/login`

| 控件 | 调用 | 后端行为 |
|---|---|---|
| 微信一键登录（主） | `doLogin(false)` | 未绑定 → 建临时账号 + 发 JWT |
| 我已有账号，用密码绑定（次） | `doLogin(true)` | 未绑定 → 只发 10 分钟票据 |

`bindRequired=true` 时切到 `bind` 阶段展开账号密码表单（票据 10 分钟，表单同页不跳转）。

**这两个调用方向不能写反**：写反则新用户看到密码表单、老用户白建一个空账号。
`tests/test_r272_account.py::test_login_defaults_to_auto_signup` 守着。

### 账号页 `pages/account`

三块：当前身份（临时账号 / 已绑定邮箱）、绑定邮箱（发码 → 倒计时 → 6 位码）、退出登录。

绑定流程：

```
输入邮箱 → POST /auth/email/send-code
          → 起倒计时（用后端 resendAfter，不用前端硬编码 60）
输入验证码 → POST /auth/email/verify
          ├ 成功且 merged → auth.persist(新 token) + 弹「已合并到原账号」
          ├ 成功未合并    → toast「邮箱绑定成功」
          └ 50512        → wx.showModal 展示数据摘要 → 用户确认后带 discardShadowData=true 重提
```

**为什么归并后必须替换 token**：归并会把当前 userId 换成老账号的 userId。沿用旧 token
访问会得到「登录成功但所有列表为空」——这比直接 401 难排查得多。`EmailBindVO` 必带
新 token，前端 `auth.persist` 整份覆盖（不是 merge 字段）。

**为什么 50512 要二次确认**：它代表「临时账号里已经有你背过的词」，继续就意味着丢弃。
一次点击抹掉两周的复习记录，是不可接受的产品行为。

### 入口位置

- 生词本页顶部窄提示条（仅 `wechatShadow=true` 显示），点击进账号页；
- 数据页页尾「账号与绑定」。

不做强制拦截弹窗：工具型小程序的第一次体验不该被表单打断；提示条足够让用户知道
「这个账号是临时的」。

## 3. 数据来源

`api.getUser()` 里的 `wechatShadow / email / emailVerified` 由登录响应与绑定响应写入
（`WxLoginVO` 与 `EmailBindVO` 同名字段）。这两个字段是账号页与提示条的唯一依据，
所以 `auth.persist` 必须把它们一起存——漏存会导致「绑定成功但提示条还在」。

## 4. 部署顺序（重要）

**先 moon-well R240，再发小程序。** 旧后端会对主按钮回 `bindRequired=true`，
新用户被带到「绑定已有账号」表单（旧行为，功能可用但体验倒退，且新用户卡住）。
小程序有审核周期，先发后端天然安全。

## 5. 未做

- 改昵称/头像：仍由网页端决定。
- 解绑微信 / 换绑邮箱：后端没有端点，页面上也不放按钮（放了就是死链）。
- 手机号绑定：不做。
